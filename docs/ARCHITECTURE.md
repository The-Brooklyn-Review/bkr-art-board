# Architecture

TBR Art Board is an internal review tool for The Brooklyn Review's art submissions. It imports submissions from Submittable, renders every page/image into browsable assets, and gives editors a fast grid + lightbox to review, tag, and select work.

## Data flow

```
Submittable (external, read-only)
        │  scripts/process-submission.ts
        ▼
Postgres (Supabase)  +  Cloudflare R2 (private object storage)
        │                        │
        │  signed URLs           │  rendered images (large + thumbnail)
        ▼                        ▼
              Review UI (Next.js App Router)
                        │
                        │  scripts/tag-all-artwork.ts (optional, quarterly)
                        ▼
              Claude API → autoGeneratedTags
```

1. **Import** — `scripts/process-submission.ts` pulls submissions from the Submittable API (metadata, cover letters, uploaded files) and writes them to Postgres. For each uploaded file, it renders PDF pages (or the image itself) into full-size + thumbnail WebP images, classifies each page (`artwork` vs. `cover_statement` / `cv_bio` / etc. — see [`src/lib/processing/classify.ts`](../src/lib/processing/classify.ts)), crops to the artwork region where relevant ([`crop.ts`](../src/lib/processing/crop.ts)), and uploads both sizes to R2.
2. **Storage** — Postgres holds all structured data; R2 holds only the rendered images. R2 is private — the app never exposes a public bucket URL. Every image is served through a short-lived **signed URL** generated on demand (`getSignedR2Url` in [`src/lib/storage/r2.ts`](../src/lib/storage/r2.ts)); nothing that reaches the browser is a permanent link, and a signed URL that leaks becomes useless once it expires.
3. **Review** — the Next.js app (`src/app/art-library`, `src/app/submissions/[id]`) reads from Postgres and R2 to render the grid and detail views. Curator actions (accept/reject recommendation, visibility, notes, thumbnail selection) are written through `src/lib/actions/mutations.ts` and logged to an append-only audit table.
4. **Tagging** (optional, quarterly) — `scripts/tag-all-artwork.ts` sends visible artwork images and artist statements to the Claude API and writes the resulting tags back to Postgres. See [`TAGGING.md`](./TAGGING.md).

## Data model — three tiers

The schema (`prisma/schema.prisma`) separates data by where it comes from and how mutable it is. This distinction matters more than the individual columns:

| Tier | Tables | Mutability |
|---|---|---|
| **Source-imported** | `SubmittableSubmission`, `SubmittableLabel`, `SubmissionLabel`, `SubmissionFile` | Mirrors Submittable. Written once by the importer; never synced back to Submittable, never edited through the app. |
| **Generated** | `ArtAsset` | One row per rendered page/image, with computed thumbnails, extracted text, and page classification. Written by the processing pipeline; can be regenerated by re-running the importer for a file (see [`OPERATIONS.md`](./OPERATIONS.md) on reprocessing). |
| **Local review state** | `ReviewAction`, `ReviewNote`, plus recommendation/visibility/note/thumbnail fields on the other tables | The app's own workflow state. The only tier written through the UI, always via `src/lib/actions/mutations.ts`. |

`autoGeneratedTags` on `ArtAsset` sits in the generated tier but is populated later, asynchronously, by the tagging script — not by the importer.

## Key relationships

- `SubmittableSubmission` → `SubmissionFile` (1:N) → `ArtAsset` (1:N): a submission has one or more uploaded files, and each file expands into one or more visible/hidden assets (PDF pages or a single image).
- `SubmittableSubmission` ↔ `SubmittableLabel` (N:N via `SubmissionLabel`): Submittable's own labels (e.g. "Consider"), imported as-is.
- `SubmittableSubmission.thumbnailAssetId` → `ArtAsset` (nullable FK, `ON DELETE SET NULL`): the curator's chosen cover image for a submission. Deleting the referenced asset (e.g. during reprocessing) clears this reference rather than blocking the delete — the app relies on that behavior to preserve a thumbnail selection across reprocessing when possible, and to fail safe (cleared, not orphaned) when it isn't.
- `ArtAsset` → `ReviewAction`, `ReviewNote` (1:N): every curator action and note is scoped to a submission and, optionally, one specific asset.

See `prisma/schema.prisma` directly for the full column list and constraints — it's kept short enough to read in one sitting and is the source of truth, not this doc.

## Auth

Single shared password (`APP_PASSWORD`), not per-user accounts — this is a small internal tool, not a multi-tenant product. Session state is an `httpOnly` cookie set by `src/app/login/actions.ts`; passwords are compared with a timing-safe check, and post-login redirects are validated against open-redirect payloads (`safeNextPath`).

## Frontend

Next.js App Router, two main surfaces:

- **Art Library** (`src/app/art-library`) — the primary review grid, with a lightbox for full-size viewing, client-side fuzzy search (Fuse.js) over titles/artists/tags, and density/filter controls.
- **Submission detail** (`src/app/submissions/[id]`) — a single submission's files, cover letter, and per-asset review actions.

Images load lazily with hover-prefetch and adjacent-slide prefetching in the lightbox to avoid pop-in when paging through full-resolution artwork.
